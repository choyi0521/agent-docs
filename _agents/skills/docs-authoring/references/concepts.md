# Concepts

A Concept develops a principle, mechanism, boundary, or trade-off that lookup
facts alone cannot explain. Write without assuming repository knowledge, then
introduce implementation detail only when it creates causal understanding.

## Shape

1. State the reader question and why the answer changes understanding or use.
2. Locate the subject in the whole product. Name its trigger, result, owners,
   boundaries, and exclusions.
3. Give an orienting model before internal names.
4. Run one sanitized concrete case from entry to observable result.
5. Explain stages in causal or lifecycle order, including ownership and state.
6. Trace refusal, failure, rollback, teardown, and incomplete paths when they
   change the model.
7. State consequential costs, limits, and trade-offs.
8. Link exact facts to Reference, procedures to Guides, and repository changes
   to Development.

Give each durable idea one canonical owner. Use a directory only when child
pages answer independently useful questions. Its index routes readers; it does
not repeat each child contract.

## Figures

Consider three lenses for a cross-boundary Concept: context and ownership, the
main flow or state change, and failure or contrast. Use every lens whose absence
would force the reader to reconstruct the mechanism from prose. Distinguish
available, partial, absent, and intended paths without relying on color alone.
Follow the technical-figure skill and its visual-semantics contract linked from
`SKILL.md` before composing or materially redesigning a figure.

## Current and intended models

State the present cutoff where it matters. Put intended behavior in the local
Plan that owns it. A page may contain substantial future design when current
and intended claims remain unmistakable. Current source cannot prove an
intended target.
