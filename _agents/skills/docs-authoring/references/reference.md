# Reference

A Reference page lets a reader look up a named public surface, observable
behavior, limit, compatibility fact, configuration value, error, schema,
protocol, contract, or required notice. Organize for random access.

## Shape

1. State what the page covers, who uses it, and what it excludes.
2. Add an **At a glance** table only when readers compare a closed set.
3. Organize entries by stable keys readers already possess.
4. For each entry, state the applicable shape, accepted values, result,
   ownership, lifetime, invariants, refusal, and cost. Omit irrelevant fields.
5. Cover boundaries, lifecycle, failures, limits, and compatibility.
6. State implementation status when it changes what readers can rely on.
7. Link related models, procedures, repository workflows, source, and tests.
8. End evidence-bearing leaf pages with one final `References` section.

## Verify the applicable surface

Read public declarations, implementation, package or build registration,
focused tests, and published authorities. Check operations, fields, cases,
errors, configuration, lifetime, invalidation, and non-obvious cost within the
page boundary. Do not infer completeness from one representative declaration.

Use temporary notes for a large surface, then discard them. Do not create a
parallel public status database. Check both directions: every applicable key
has a documented owner, and every documented key still exists.

## Use code as evidence

Show an exact declaration or transition only when its shape changes correct
use. Lift the smallest consequential source region and explain its meaning.
Fold supporting evidence only when the page remains complete while it is
closed. A test does not replace the production source whose contract the page
explains.

Keep available entries outside Plan containers. Put intended signatures,
fields, limits, failures, or behavior in a local Plan and label them as targets.
