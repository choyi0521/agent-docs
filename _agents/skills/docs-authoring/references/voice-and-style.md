# Voice and style

## Voice

Write plain technical English. Lead with the result or fact the reader came
for. Use active voice and name the actor. Keep one main idea in each sentence
and one subject in each paragraph. Reuse names from the published contract; do
not rotate terms for variety.

Address the reader as `you` only in executable procedures. Distinguish an
expected refusal, a violated invariant, and an unsuccessful command instead of
calling every outcome an error.

Avoid sales language, conversational filler, and claims such as `obviously`,
`simply`, `seamlessly`, `robust`, or `powerful` unless a cited source requires
the term.

## Sentences and headings

- Prefer one clause and put qualifications beside the claim they limit.
- Split asides and semicolon chains. Avoid em dashes.
- Define a term before another definition depends on it.
- Use one H1, start content at H2, and do not skip heading levels.
- Use short sentence-case headings. Procedures name the next result or action;
  explanatory and lookup pages name the subject.

## Organization

Establish the whole before naming its parts. Locate the subject in the product
and name inputs, outputs, owners, and boundaries before opening source details.
Order sections by the reader's task, causal path, lifecycle, or lookup keys,
not by directory, declaration, or discovery order.

Concision governs expression, not scope. Preserve orientation, relationships,
and consequential exception paths.

## Examples, code, and tables

Use sanitized values from a reproducible test or supported command. Never copy
secrets, tokens, private endpoints, customer data, or machine-specific paths.
Put the first useful example near the beginning.

Code proves an exact shape or executable path; prose explains its meaning.
Before a block, state the question it answers. Interpret the inputs, outputs,
ownership, lifetime, state change, refusal, recovery, or cost that affects use.

Use a table only when readers compare a closed set across the same fields. Use
prose or a figure for sequence, cause, or argument. Avoid repeated large code
blocks separated by brief remarks.

## Status and time

State durable facts. Avoid `new`, `recently`, `currently`, and `soon` unless a
version or date is part of the fact. Write available behavior in the present
tense and intended behavior in the configured Plan container. Keep progress,
assignments, percentages, and dates in the tracking system.

Read the page aloud once. Remove sentences that require a second reading and
verify that terms, outcomes, and section order remain consistent.
