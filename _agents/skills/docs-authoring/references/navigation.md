# Navigation and reorganization

The documentation root page is the product overview. It names the public
boundary, orients a new reader, and routes to configured sections.

The audit configuration declares section paths, reader roles, and root order.
Do not assume fixed names or create placeholder sections. Common reader roles
are `guide`, `concept`, `reference`, and `development`, but a project may choose
different public labels and ordering.

Use reader need as the first navigation axis. Do not mirror source directories,
package trees, specification assemblies, or organizational charts into public
navigation. Those structures provide evidence, not reader intent.

Every populated directory needs the configured index file and explicit ordered
navigation. An index states the set boundary, describes each child, and names a
starting point. It does not become the sole owner of detailed contracts.

## Reorganize deliberately

Before changing a root or section boundary, inspect pages, incoming links,
navigation instructions, and each page's reader question. For a substantial
proposal, show the current tree, proposed tree, move or deletion map, and link
impact before editing.

Choose titles and boundaries from current public vocabulary. Preserve an old
path only when an external URL contract requires it. Move, merge, split, rename,
or delete pages to give durable claims one owner. Do not retain duplicate
introductions or parallel indexes without a current contract.

Update links, root navigation, figures, snippets, and generated surfaces. Run
the configured audit and build, then inspect rendered navigation.
